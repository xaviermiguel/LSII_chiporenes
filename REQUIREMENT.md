# ProTube — MVP Requirements Specification

This document breaks down the MVP feature list defined in [README.md](./README.md#mvp) ("EVALUATION (6)") into
Agile-style requirements: user stories with acceptance criteria for user-facing features, and non-functional
requirements (NFRs) for engineering/process constraints. Story points use the Fibonacci scale (1, 2, 3, 5, 8, 13) as
a rough sizing guide and should be re-estimated by each team during backlog refinement.

Priority follows MoSCoW (Must have / Should have / Could have / Won't have this time).

---

## Epic 1 — Authentication

### US-01: User registration

**As a** visitor, **I want** to create an account with an email and password, **so that** I can access the
features reserved for registered users.

**Acceptance criteria**

* Given a visitor on the registration page, when they submit a valid email, password and required profile fields,
  then an account is created and they are redirected to a logged-in state.
* Given a visitor submits an email that is already registered, when they submit the form, then a clear error is
  shown and no duplicate account is created.
* Given a visitor submits an invalid email or a password that doesn't meet the minimum policy, when they submit
  the form, then validation errors are shown and no account is created.

**Priority:** Must have · **Estimate:** 3

### US-02: User login

**As a** registered user, **I want** to log in with my credentials, **so that** I can access my account and
authenticated features.

**Acceptance criteria**

* Given a registered user on the login page, when they submit correct credentials, then they are authenticated and
  redirected to the home page.
* Given a registered user submits incorrect credentials, when they submit the form, then an error is shown and no
  session is created.
* Given an authenticated user, when their session expires or they log out, then they lose access to authenticated
  features until they log in again.

**Priority:** Must have · **Estimate:** 2

## Epic 2 — User profile

### US-03: View and edit profile

**As a** registered user, **I want** to view and edit my profile (avatar, description, etc.), **so that** other
users can know more about me and my content.

**Acceptance criteria**

* Given an authenticated user on their profile page, when the page loads, then their avatar, description and other
  profile fields are displayed.
* Given an authenticated user editing their profile, when they save valid changes, then the changes are persisted
  and reflected immediately.
* Given any user viewing another user's public profile, when the page loads, then only public profile information
  is shown (no edit controls).

**Priority:** Must have · **Estimate:** 3

---

## Epic 3 — Video catalog & playback

### US-04: Browse video list

**As a** user (authenticated or not), **I want** to see a list of available videos, **so that** I can discover
content to watch.

**Acceptance criteria**

* Given the home/list page, when it loads, then videos generated by the `videoGrabber` tool (or uploaded by users)
  are displayed with at least title and thumbnail.
* Given a list of videos larger than one page/screen, when the user scrolls or paginates, then additional videos
  are loaded without errors.

**Priority:** Must have · **Estimate:** 3

### US-05: Play a video and view its details

**As a** user, **I want** to play a video and see its information (title, description, comments, etc.), **so
that** I can watch and understand the content.

**Acceptance criteria**

* Given a video in the catalog, when the user opens it, then the video player starts and plays the video file.
* Given a video is playing, when the detail page is shown, then title, description and existing comments are
  visible alongside the player.
* Given a video ID that doesn't exist or isn't available, when the user navigates to it, then a not-found state is
  shown instead of a broken player.

**Priority:** Must have · **Estimate:** 5

---

## Epic 4 — Video upload & management

### US-06: Upload a video

**As an** authenticated user, **I want** to upload a video, **so that** other users can discover and watch it.

**Acceptance criteria**

* Given an authenticated user on the upload page, when they submit a supported video file with required metadata
  (title, description), then the video is stored and appears in the catalog.
* Given an unauthenticated user, when they try to access the upload page, then they are redirected to log in.
* Given an upload that fails (unsupported format, size limit, network error), when the failure occurs, then the
  user sees a clear error and no partial/corrupt video is published.

**Priority:** Must have · **Estimate:** 5

### US-07: Edit video metadata

**As an** authenticated user, **I want** to edit the metadata of my videos (tags, description, category, etc.),
**so that** I can keep my content accurate and discoverable.

**Acceptance criteria**

* Given a video owned by the authenticated user, when they edit tags, description or category and save, then the
  changes are persisted and visible on the video detail page.
* Given a video not owned by the authenticated user, when they attempt to edit it, then the action is denied.

**Priority:** Must have · **Estimate:** 3

---

## Epic 5 — Search

### US-08: Search videos

**As a** user, **I want** to search videos by title, description, etc., **so that** I can quickly find content
I'm interested in.

**Acceptance criteria**

* Given a search query matching one or more videos' title or description, when the user searches, then matching
  videos are returned, ranked by relevance.
* Given a search query with no matches, when the user searches, then an empty-state message is shown (no error).
* Given an empty search query, when the user searches, then either all videos are shown or the action is a no-op
  (behavior defined by the team), but the app must not error.

**Priority:** Must have · **Estimate:** 5

---

## Epic 6 — Comments

### US-09: Comment on a video

**As an** authenticated user, **I want** to comment on a video, **so that** I can share my opinion with other
users.

**Acceptance criteria**

* Given an authenticated user on a video detail page, when they submit a non-empty comment, then it is persisted
  and displayed under the video.
* Given an unauthenticated user, when they try to comment, then they are prompted to log in.

**Priority:** Must have · **Estimate:** 3

### US-10: Reply to and like comments

**As an** authenticated user, **I want** to reply to comments and like them, **so that** I can engage in
discussion around a video.

**Acceptance criteria**

* Given an existing comment, when an authenticated user submits a reply, then the reply is persisted and displayed
  nested under the original comment.
* Given an existing comment, when an authenticated user likes it, then the like count increases and reflects the
  user's like state; when they unlike it, the count decreases.

**Priority:** Should have · **Estimate:** 5

---

## Epic 7 — Analytics

### US-11: View analytics for my videos

**As an** authenticated user, **I want** to see analytics for my videos, **so that** I can understand how my
content is performing.

**Acceptance criteria**

* Given an authenticated user with uploaded videos, when they open the analytics page, then they see metrics
  (e.g. views, comments, likes) relevant to their own content.
* Given a user with no uploaded videos, when they open the analytics page, then an empty state is shown instead of
  an error.

**Priority:** Must have · **Estimate:** 5

## Non-functional & engineering requirements

These are cross-cutting constraints that apply to the whole MVP rather than a single feature. They belong in the
team's **Definition of Done** and should be verified every sprint, not tracked as one-off stories.

### NFR-01: Persistent storage

**Requirement:** Application data must be persisted in a real database, not in memory and not H2.

**Rationale:** In-memory/H2 storage doesn't survive restarts and isn't representative of a production setup.

**Acceptance criteria**

* Given the application is restarted, when it comes back up, then previously created data (users, videos,
  comments, etc.) is still available.
* Given the codebase, when inspected, then no in-memory or H2 datastore is used for the delivered application.

**Priority:** Must have

### NFR-02: Automated end-to-end tests

**Requirement:** The application must have E2E tests (e.g. Cypress, Selenium) covering the golden paths of the
MVP features.

**Acceptance criteria**

* Given the E2E suite, when it runs against a fresh environment, then it exercises at least authentication, video
  upload/playback, search and commenting.
* Given a regression is introduced in a covered flow, when the E2E suite runs, then it fails.

**Priority:** Must have

### NFR-03: Containerized delivery

**Requirement:** The application must be delivered using containerization (e.g. `docker-compose`).

**Acceptance criteria**

* Given a clean machine with Docker installed, when `docker-compose up` (or equivalent) is run, then the full
  application (backend, frontend, database) starts and is usable without manual setup steps.

**Priority:** Must have

### NFR-04: CI validation pipeline

**Requirement:** Changes must be validated through a CI pipeline (e.g. GitHub Actions) before merging.

**Acceptance criteria**

* Given a pull request, when it is opened or updated, then the CI pipeline automatically runs build, lint and
  tests.
* Given the CI pipeline fails, when reviewers look at the PR, then the PR is blocked from merging until it passes.

**Priority:** Must have

### NFR-05: Test coverage

**Requirement:** The whole application must be well tested, with more than 50% code coverage.

**Acceptance criteria**

* Given the test suite, when coverage is measured, then overall coverage is above 50%.
* Given a coverage report, when reviewed each sprint, then the team tracks it does not regress below the
  threshold.

**Priority:** Must have

### NFR-06: AI configuration setup

**Requirement:** Before using AI in the project, the team must define, agree on and commit configuration file(s)
for the AI tool(s) used, following that tool's best practices (see [Usage of AI](./README.md) in the README).

**Rationale:** A shared, reviewed configuration keeps AI-assisted work consistent across the team and gives
everyone the same guardrails from the start, instead of each member improvising their own setup.

**Acceptance criteria**

* Given an AI tool the team wants to adopt, when its configuration is proposed, then it is reviewed and approved
  by the team before anyone uses that tool on the project.
* Given an approved AI configuration, when it is finalized, then it is committed to the repository so all members
  use the same configuration.
* Given the configuration already in use, when a member wants to change it, then the change follows the same
  review/approval process as the initial setup.

**Priority:** Must have

### NFR-07: Preservation of AI prompts

**Requirement:** Every prompt used to generate code, architecture or other project artifacts with AI must be
preserved and committed to the repository, inside a dedicated folder, and used consistently by all members of the
team. Prompts must be agreed on and reviewed by the team, and approved before being used in the project.

**Rationale:** Preserving prompts makes AI-assisted work traceable and reviewable during the exam, and lets the
team reuse and improve prompts that already work well instead of everyone reinventing their own.

**Acceptance criteria**

* Given the repository, when set up for AI usage, then a dedicated folder (e.g. `/prompts`) exists to store
  prompts before any AI-generated contribution is committed.
* Given a new prompt someone wants the team to use, when it is proposed, then it is reviewed and approved by the
  team before being adopted.
* Given an approved prompt used to generate code, architecture, etc., when the resulting change is committed, then
  the prompt itself is also committed to the `/prompts` folder (e.g. alongside the PR that used it).
* Given a task type already covered by an approved prompt in `/prompts`, when any member performs that task with
  AI, then they reuse the agreed prompt rather than creating an ad hoc one, or propose an update to it through the
  same review process.

**Priority:** Must have

## Backlog notes

* Each user story above is a starting point for refinement, not a final spec — teams should split, re-word or
  re-estimate stories during Refinement/Grooming as described in the README's [Agile ceremonies](./README.md).

  README. Items beyond this list belong to the [Improvements](./README.md) section and should be written as new
  stories once selected by the team.
